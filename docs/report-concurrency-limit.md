# 同時リクエスト数の上限(3)の計測報告

- 計測日: 2026-09-29
- 対象: `feature/concurrency-limit` ブランチ。変更前 = 基準コミット `e04aac2`(タグ `before-concurrency-limit`)
- 指示書: `docs/tasks/task-concurrency-limit.md`
- 仕様: SPEC 3.6e

## 結論

- **同時接続数: 変更前 最大11本 → 変更後 最大3本**(9回とも)
- **グラフが出るまでの時間(展開)は変わらない。** 検索直後は展開(high)しか通信が無いため
- **閲覧数(球の大きさ)が揃うまでと、サイドバーが出るまでは、同じか最大で約0.4秒遅い。**
  ただし回ごとのばらつき(同じ記事で最大約1秒)と同じくらいの大きさで、はっきりした差とは言えない
- 許容できるかどうかは、人が実際に触って判断してください(下の「確認してほしいこと」)

## 計測のしかた

指示書の手順2は `window.__viz.measure()` で測る想定でしたが、**`measure()` は画面上の配置(px)を測る道具で、
表示までの時間は測りません。** そこで次の方法で測りました。

1. `?debug=1` を開き直す(メモリ上のキャッシュを空にする)
2. ページの `window.fetch` を包み、送信と完了の時刻、同時に開いている接続数を記録する
3. 検索欄に記事名を入れて確定し、通信が2秒止むまで待つ
4. 時刻は確定からの経過(ms)

記事は 初音ミク / 東京タワー / 量子力学 を各3回。開発サーバー(`npm run dev`)、同じ回線・同じ日に連続して測りました。

列の意味:

| 列 | 意味 |
|---|---|
| 最大同時 | 同時に開いていた接続数の最大 |
| 展開 | 展開の Action API(A1〜A5)がすべて終わった時刻 ≒ グラフが出た時刻 |
| 閲覧数(表示分) | 表示ノード25件の閲覧数が揃った時刻 ≒ 球の大きさが揃った時刻 |
| 閲覧数(全部) | 先読み8件を含めて揃った時刻 |
| サイドバー | 現在地のプレビュー・カテゴリ・被リンク数が揃った時刻 |

## 実装で決めたこと(指示書に書かれていなかった点)

- **閲覧数(表示分)は `mid`。** 指示書は「低 = 先読み」とだけあり、表示分の段が無かった。
  表示分を先読みより先に取る決まりを守るため、サイドバーと同じ `mid` にした。
  このため、到着直後のサイドバーは表示分の閲覧数(最大25件)の後ろに並ぶ。上の計測でサイドバーが遅れうるのはこのため
- **検索候補(A8)は `high`。** 指示書の3段階に無かった。入力中の利用者が直接待っているので展開と同じ段にした
- **接続の枠は本文を読み終えるまで持つ。** 応答のヘッダが届いた時点で枠を返すと、本文の受信中の接続が数に入らず、
  Network タブでは3本を超えて見えるため。これに合わせて `fetchWithTimeout` は Response ではなく、
  本文を読み込み済みの `{ ok, status, text(), json() }` を返すようにした(呼び出し側はこの4つしか使っていない)。
  15秒のタイムアウトも本文の受信まで含むようになった(以前はヘッダが届いた時点で止めていた)
- **サイドバーは、取り消されたら結果を保存しない。** プレビューとメタ情報の片方だけ取り消された場合も、両方保存しない
  (送信済みだったメタ情報は `fetchArticleMeta` 側のキャッシュに残る)
- `scripts/fetch-long-walks.mjs` も同じ行列を通る。1記事ずつ直列に展開するので、影響は展開内の同時4本が3本になることだけ。
  スクリプトは `globalThis.fetch` を包んで User-Agent を付けているが、行列は送信の時点で `fetch` を呼ぶので、そのまま効く

## 確認できなかったこと
