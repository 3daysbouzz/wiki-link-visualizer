## 訂正: 初回計測はキャッシュの影響を受けていた

閲覧数の REST API(R1)の応答はブラウザにキャッシュされる。初回は同じ記事を「変更前 → 変更後」の順に測ったため、
変更後の閲覧数はほぼキャッシュから返っていた(応答時間の中央値 1ms。Action API は 600ms 前後で、キャッシュされていない)。
そのため、閲覧数とサイドバーの遅れが実際より小さく出ていた。

2026-09-30 の計測では、計測用のビルドだけ `fetch` に `cache: 'no-store'` を付けて、毎回ネットワークから取らせた
(この指定は要求ヘッダを増やさないので CORS の事前確認は起きない。コミットしたコードには入れていない)。
両方ともビルド版(`vite preview`)で、変更前と変更後を交互に、間を30〜40秒あけて測った(429 を避けるため)。

## 初回計測(2026-09-29。キャッシュの影響あり。参考)

### 計測のしかた

指示書の手順2は `window.__viz.measure()` で測る想定でしたが、**`measure()` は画面上の配置(px)を測る道具で、
表示までの時間は測りません。** そこで次の方法で測りました。

1. `?debug=1` を開き直す(メモリ上のキャッシュを空にする)
2. ページの `window.fetch` を包み、送信と完了の時刻、同時に開いている接続数を記録する
3. 検索欄に記事名を入れて確定し、通信が2秒止むまで待つ
4. 時刻は確定からの経過(ms)

記事は 初音ミク / 東京タワー / 量子力学 を各3回。開発サーバー(`npm run dev`)、同じ回線・同じ日に連続して測りました。

| 列 | 意味 |

| 最大同時 | 同時に開いていた接続数の最大 |
| 展開 | 展開の Action API(A1〜A5)がすべて終わった時刻 ≒ グラフが出た時刻 |

## 実装で決めたこと(指示書に書かれていなかった点)

- **(2026-09-30 に `views` へ変更。下の「レビュー指摘の修正」)** 閲覧数(表示分)は `mid`。指示書は「低 = 先読み」とだけあり、表示分の段が無かった。
  表示分を先読みより先に取る決まりを守るため、サイドバーと同じ `mid` にした。
  このため、到着直後のサイドバーは表示分の閲覧数(最大25件)の後ろに並ぶ。上の計測でサイドバーが遅れうるのはこのため
- **検索候補(A8)は `high`。** 指示書の3段階に無かった。入力中の利用者が直接待っているので展開と同じ段にした
- **接続の枠は本文を読み終えるまで持つ。** 応答のヘッダが届いた時点で枠を返すと、本文の受信中の接続が数に入らず、
  Network タブでは3本を超えて見えるため。これに合わせて `fetchWithTimeout` は Response ではなく、
  本文を読み込み済みの `{ ok, status, text(), json() }` を返すようにした(呼び出し側はこの4つしか使っていない)。
  15秒のタイムアウトも本文の受信まで含むようになった(以前はヘッダが届いた時点で止めていた)
- **サイドバーは、取り消されたら結果を保存しない。** プレビューとメタ情報の片方だけ取り消された場合も、両方保存しない
  (送信済みだったメタ情報は `fetchArticleMeta` 側のキャッシュに残る)
- `scripts/fetch-long-walks.mjs` も同じ行列を通る。1記事ずつ直列に展開するので、影響は展開内の同時4本が3本になることだけ。
  スクリプトは `globalThis.fetch` を包んで User-Agent を付けているが、行列は送信の時点で `fetch` を呼ぶので、そのまま効く

## 中止した通信をキャッシュしないこと(2026-09-30 追加)

サイドバーの読み込みを `src/api/sidebarData.js` の `loadSidebarData` に切り出し、次をテストで固定した
(`tests/wikipedia.test.js` の「loadSidebarData: 取り消しと保存」)。

- 閲覧数で枠が埋まっている間にホバーし、別のノードへ移って取り消すと、何も保存せず、送信もしない
- そのあと同じノードを選ぶと取り直し、プレビューとメタ情報が出る
- 本当に失敗したもの(HTTP 500 等)は、以前どおり保存して取り直さない

このテストは、取り消し時に null を保存するようにわざと壊すと失敗することを確かめてある。

## 確認できなかったこと

- **ホバー連打のときの Network タブの目視(指示書の手順6)。** 作業に使ったブラウザ画面が非表示の状態で、
  描画のフレームが進まず、3D 画面のホバーを起こせなかった。取り消しの動きはユニットテストで確かめている

1. `npm run dev` で開き、Network タブを `wikipedia` で絞り込んで、

   - ノードの上をカーソルで次々になぞったとき

2. 体感の遅さ。特に「到着してからサイドバーの文章が出るまで」と「経路の URL を開いてから球の大きさが揃うまで」
3. 比べたいときは `?debug=1&maxConcurrent=8` で上限を変えられる(1〜16。開発サーバーだけ。本番ビルドでは 3 より上げられない)

## レビュー指摘の修正(2026-09-30。`docs/tasks/task-concurrency-review-fixes.md`)

### 事前の確認3点

| 確認 | 結果 |
|---|---|
| 1. 検索候補の取り消し | 対応済み。`TopBar.jsx` は `fetchSuggestions(q, limit, { signal })` に渡し、新しい入力・確定・画面を離れるときに古い分を `abort` している |
| 2. `fetchPageviews` を `'high'` で呼ぶ箇所 | 無い。呼び出しは `App.jsx` の2か所(既定と `'low'`)と `measure.js` の2か所(既定)。残っている `priority: 'high'` は検索候補(`fetchSuggestions`)の1か所だけで、意図どおり |
| 3. 戻り値を Response 扱いしている箇所 | 無い。`src/`・`scripts/`・`tests/` で使っているのは `ok`・`status`・`json()`・`text()` だけ(`.clone()` の一致は three.js のベクトル、`.url` はプレビューの独自オブジェクト、`headers` はスクリプトの要求ヘッダで、いずれも無関係) |

### 修正

1. **優先度を4段階にした**: `high`(展開・検索候補)→ `mid`(サイドバー)→ `views`(表示中の閲覧数)→ `low`(先読み)。
   `fetchPageviews` の既定を `views` にした。先読みの `low` は変えていない
2. **本番ビルドでは URL から上限を上げられない**: `effectiveMaxConcurrent`(`urlState.js`)で、本番ビルドは `MAX_CONCURRENT_REQUESTS` に丸める。
   開発サーバーでは従来どおり 1〜16。ビルド版で `?debug=1&maxConcurrent=16` を開いて検索し、最大同時が 3 だったことも確かめた
3. **`fetchWithTimeout` の戻り値に `headers` を足した**(次の 429 対応のため)

テスト: 406 → 416件(追加10件)。サイドバー順のテストは、優先度の並びを元に戻すと失敗することを確かめてある。
