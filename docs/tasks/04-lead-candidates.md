# タスク04: 冒頭リンクで、取得上限から漏れた候補を補う(案A)

CLAUDE.md と SPEC.md(3.2〜3.5)を読んでから着手すること。
前提: タスク01(合計スコア方式。wMutual / wLead)が完了していること。

## 背景

タスク01の後に行った重みづけの追加検証(連想ゲーム的な組210組。レポートはリポジトリに含めていない)で、次の取りこぼしが分かった。

- `generator=links` は本文のリンクを **リダイレクト解決前の名前のコードポイント順**(数字 → 英字 → かな → 漢字)で返す。
  `MAX_CONTINUE=3`(1,500件)で打ち切られる大きい記事では、**漢字で始まる記事が候補(candidates)にそもそも入らない**。
  重みをどう変えても救えない(検証した202記事中22記事が打ち切り)
- 冒頭リンク(parse・section=0)は別のリクエストで取っていて、この上限の影響を受けない
- よって「冒頭リンクにあるのに候補に無い」記事を候補に足せば、この型の取りこぼしを直接救える

## 指示書の原案からの変更点(レビュー結果)

原案(案Aの依頼文)を実データと現行コードで確かめ、次の4点を直した。

| # | 原案 | 問題 | この指示書での扱い |
|---|---|---|---|
| 1 | 追加の API 呼び出しはしない | 冒頭リンク(parse)の名前は **リダイレクト解決前** で、しかも **赤リンク(存在しない記事)** も含む。解決に使っている `query.redirects` は `generator=links` の応答から集めたもので、**打ち切られた後ろ側の記事のリダイレクトは入っていない**。そのままでは誤った名前・存在しない記事が候補に入る。また相互リンク(mutual)は `generator=links` に相乗りして取っているので、追加候補の相互リンクは **追加のリクエスト無しには判定できない** | **打ち切りが起きた展開に限り**、追加候補の名前を1回の `action=query`(最大50件/回)で問い合わせ、リダイレクト解決・存在確認・長さ・相互リンクを同時に取る |
| 2 | 追加候補の morelike は「圏外」扱い | morelike(`list=search`)は **リンクの有無と無関係に** 最大500件を返すので、追加候補にも順位がありうる。一律に圏外にする理由がない | 他の候補と同じく `ranks.get(title)` を引く |
| 3 | ハブ記事(閲覧数が多い記事)の除外も適用 | 現行コードにハブ除外は **無い**(SPEC 3.4「汎用ハブの除外は行わない」)。閲覧数を順位付けに使わない方針(CLAUDE.md)とも合わない | 適用しない。除外は既存の `isExcludedTitle`(日付・年・一覧・曖昧さ回避)と中心記事自身だけ |
| 4 | 再現6組が確定枠に入ることを確認 | 実 API で確認したところ、**トヨタ自動車 → 豊田喜一郎 は冒頭リンクに無い**(冒頭69件に含まれない)。案Aでは救えない | 完了条件は「5組が候補に入る」。確定枠に入るかは結果として報告する(冒頭リンクどうしの取り合いの問題が残るので、全組が確定枠に入るとは限らない) |

なお1の「追加のリクエスト」について:
- 打ち切りの無い記事(追加検証では約9割)では、冒頭リンクは必ず候補に含まれる(冒頭のリンクは本文のリンクの一部で、
  リダイレクトも同じ応答で解決される)ので **補完は不要で、リクエストも増えない**
- 打ち切りが起きた記事では、`fetchLinks` と parse の両方が返った後に1往復(補完が50件を超えれば並列に2回)増える。
  打ち切りが起きる記事はもともと `fetchLinks` だけで3往復しているので、増分は小さい
- 実データでは、打ち切りが起きた6記事で「候補に無い冒頭リンク」は 7〜49件。うちリダイレクト名は 0〜5件で、
  リダイレクト解決後も既存の候補とは重ならなかった(=解決しないと別名の重複候補になる)。
  相互リンクだったのは 5〜29件。相互リンクを取らずに足すと、冒頭+相互の既存候補(1.4点)に常に負ける

## 仕様

### 1. 補完の条件と手順(`fetchLinkedArticles`)

`fetchLinks` と冒頭リンク(parse)の両方が返った後、素材(materials)を作る前に行う。

1. **`reachedLimit` が true で、冒頭リンクの取得に成功したときだけ** 行う。それ以外は何もしない(リクエストも増やさない)
2. 冒頭リンクの名前を既存の `redirects` で解決したもの(今の `leadSet`)のうち、
   `candidates` に無く、中心記事自身でもないものを「補完の対象」とする
3. 補完の対象を `LEAD_EXTRA_MAX`(新しい定数。100)件までに切り詰め、50件ずつ `action=query` で問い合わせる(並列)

   ```
   action=query
   titles=<補完の対象を | で連結。最大50件>
   redirects=1                … リダイレクトを解決する
   prop=info|links            … info: 長さ。links: 相互リンク
   pltitles=<中心記事>
   pllimit=max
   ```

4. 応答の `pages` のうち、`missing` / `invalid` でなく名前空間0 のものを追加候補にする(赤リンクはここで落ちる)。
   解決後の名前が既存の候補と同じなら足さない(重複させない)。同じ解決先に複数の名前が集まっても1件にする
5. この問い合わせは **補助情報** として扱う。失敗したら補完なしで続け、`console.warn` を出す(既存の `optional` を使う)
6. 追加の関数は `fetchLinks` と同じく `apiGet` を通す(`fetchWithTimeout`・エラー文言・独自ヘッダを付けない、の約束を守る)

### 2. 追加候補の素材

既存の候補と同じ形(`{title, length, rank, mutual, lead}`)にして `materials` に入れる。

- `rank`: `ranks.get(解決後の名前)`。無ければ null(圏外)
- `mutual`: 問い合わせの応答に `links` があれば 1
- `lead`: 1(冒頭リンクだから足した候補)
- `length`: 応答の `length`
- `isExcludedTitle` に当たるもの(日付・年・一覧・曖昧さ回避)は、既存の候補と同じく除外件数に数えて捨てる
  (打ち切り側は年の記事が多いので、冒頭にある「1936年」のようなものも同じ扱いにする)

スコア計算(`rankCandidates`)・プール(`POOL_SIZE`)・確定枠(`GUARANTEED_TOP`)・抽選(`pickLinks`)・
追加表示(`getMoreLinks`)は変更しない。追加候補も同じ土俵で並ぶ。`linkCache` に入る素材にも含める。

### 3. ログ

`[wikipedia]` の行の「冒頭リンクN件」の後ろに、冒頭から追加した件数を出す。

```
[wikipedia] 長嶋茂雄: 2400ms / リンク先1464件(3回取得, 上限打ち切り) / 除外: 日付等300件 / morelike一致… / 相互リンク… / 冒頭リンク45件(うち候補外から追加9件) / …
```

- 打ち切りが無いときは何も足さない(今のログのまま)
- 補完の問い合わせに失敗したときは `(候補外の補完に失敗)` と出す
- 「冒頭リンクN件」には追加分も含める(候補のうち lead=1 の件数、という意味を保つ)

### 4. 定数

`constants.js` に `LEAD_EXTRA_MAX = 100` を置く(補完の問い合わせは最大2回)。
冒頭リンクは多い記事でも177件(追加検証での最大)、候補に無いものは実測で最大49件なので、通常は1回で済む。
VizConfig には入れない(表示の調整値ではなく、取得の歯止めなので)。

## 完了条件

- `npm test` が通る。次のテストを足す(fetch を偽装する既存の方式で)
  - 打ち切りありの展開で、冒頭にあって候補に無い記事が候補に入り、相互リンク・morelike 順位が反映される
