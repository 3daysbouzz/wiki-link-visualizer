# タスク01 評価レポート: 関連スコア方式(相互リンク・冒頭リンクの加点)

作成日: 2026-09-25
対象の指示書: `docs/tasks/01-relevance-score.md`
状態: 実装済み・確認待ち(rev2 の wLead は協議のうえ 0.6 に決定。7章に最終確認の結果)

このレポートは、後からこのプロジェクトに関わる人や AI が、
「なぜ重みがこの値なのか」「何を測って何が分かったのか」をたどれるように残す。

---

## 1. 開発指示の要約

### 背景(指示書より)

友人のフィードバックとして「有名キャラクターを検索したのに担当声優が出てこない」とあった。
原因は、関連リンクの順位付けが morelike(本文の類似度)だけであること。
キャラクター記事と声優記事は本文の語彙が違うため、声優は morelike の順位が低いか圏外になる。

### 指示された仕様

順位を次の合計スコアで決める。

    score = wMorelike × m + wMutual × mutual + wLead × lead

| 要素 | 定義 |
|---|---|
| `m` | morelike の順位 r(0始まり)から `1 / (1 + r / 20)`。圏外は 0 |
| `mutual` | 候補記事から中心記事へのリンクもある(相互リンク)なら 1 |
| `lead` | 中心記事の冒頭節(section=0。インフォボックスを含む)にリンクがあれば 1 |

- 重みの初期値(rev2 プリセット): wMorelike=1.0、wMutual=0.8、wLead=0.4
  - 指示書の意図は「相互リンクは高め、冒頭リンクはほどほどに効かせる」
- current プリセットは wMutual=0・wLead=0 にして、従来と同じ順位になることを保証する
- 上位 150 件(POOL_SIZE)をプールにし、上位 10 件(GUARANTEED_TOP)は確定で出す。残りは従来どおり重み付きで抽選する

### 完了条件のうち、評価の対象にしたもの

1. キャラクター記事を3つ以上選び、**担当声優が確定枠(上位10件)に入るか**を報告する
2. `?preset=current` で従来と同じ顔ぶれになる(同じ seed で比較)
3. 展開にかかる時間の変化を比較する(目安: 悪化は1秒以内)
4. `npm test` が通る

## 2. 実装の要点

| 項目 | 内容 |
|---|---|
| 相互リンクの取得 | 既存の `generator=links` に `prop=links&pltitles=<中心記事>` を相乗り(指示書の第一案)。追加のリクエストなし |
| 冒頭リンクの取得 | `action=parse&prop=links&section=0` を既存のリクエストと並列に投げる。失敗したら加点 0 で続行 |
| リダイレクトの照合 | `generator=links` の応答の `query.redirects` で、冒頭リンクの名前を解決してから照合する |
| スコア計算 | 純粋関数 `rankCandidates(materials, weights)`。同点は長さの降順 → タイトルのコードポイント順 |
| キャッシュ | `linkCache` にはスコア計算前の素材(順位・mutual・lead・length)を保存し、取り出すたびに並べ替える。重みを変えるとキャッシュ済みの記事にも効く |
| 設定 | `wMorelike` / `wMutual` / `wLead` を VizConfig に追加(URL と leva の ranking フォルダ)。rev2 を既定のプリセットにした |

## 5. 考察

### 5.1 相互リンクの加点は、作品内の記事の中では差を生まない

相互リンクは「作品世界の外にある、関係の強い記事」を拾う手がかりとして導入した。
ところが作品内の記事(登場人物・作品名・劇場版など)も、キャラクター記事とは互いにリンクしている。
そのため上位はほぼ全員が mutual=1 になり、加点が全員に一律で乗って順位を変えない。

- 声優を押し上げたのは、実質的に冒頭リンク(lead)だけだった
- 相互リンクが効くのは、morelike 圏外の記事どうしで比べるとき(圏外の候補を長さ順ではなく関係の強さで並べ替えるとき)に限られる。これには意味があるので、加点自体は残す価値がある

### 5.2 wLead の決め方

- 声優の m は 0.16〜0.29 と低い。確定枠の10位は 1.47〜1.58 なので、冒頭の加点に 0.2 前後の上積みが要る
- wLead=0.6 なら、wMutual(0.8)より低いまま「相互は高め、冒頭はほどほど」を保てて、5記事中4記事で確定枠に入る
- 孫悟空のように冒頭リンクが多い(17件)記事では、wLead を上げても冒頭リンクどうしで確定枠を取り合うため、1.0 でも届かない
  - 重みの調整だけで全記事を確定枠に入れるのは難しい
- 冒頭リンクに汎用語が混ざることは、wLead を上げすぎない理由になる
  - 汎用語は相互リンクでないことが多いため、wLead=0.6 なら加点は 0.6 だけで、morelike の13位相当にとどまる

### 5.3 協議の結果(2026-09-25)

- rev2 の wLead は **0.6** にする(利用者が同意)
- 完了条件1は「5記事中4記事で確定枠に入る。孫悟空は17位」として報告する
- 所要時間は複数回測り直して判断する(7章)

### 5.4 表示件数についての検討(利用者からの提起)

利用者の意見: 場合によっては、1記事から出す件数(neighborLimit)や抽選で出す件数を減らすことも考えた。
この後の実装(02 の追加表示など)で表示ノードが増えるため。

検討の結果:

- **表示件数を減らすことには賛成。** CLAUDE.md の目的「大量のノードを見せることは目的ではない。次にどれをクリックするか判断しやすくする方を優先する」にも合う
- ただし、**neighborLimit を減らしても、声優が出る確率は上がらず、むしろ下がる。**
  確定枠は10件で固定なので、減るのは抽選枠。11〜17位にいる声優は抽選で拾われる機会が減る
- 02 の追加表示は、未表示の候補を**抽選なしでスコア順に**出す。
  初期表示を減らしても、11位以降の関係の強い記事(声優を含む)は、最初の「追加」でまとめて出てくる
- 考えられる組み合わせ:
  - (A) 初期表示を減らし(例: 40 → 24〜30)、足りなければ 02 の追加で増やす
  - (B) 確定枠と抽選枠の比率を変える(例: GUARANTEED_TOP を 10 → 15)
    - 声優が確定枠に入る記事は増えるが、散歩の偶然性(下位の記事に出会える)は減る
- 判断は 02 の実装後に、同じ seed・同じ記事で見比べて決めるのがよい。
  neighborLimit はすでに VizConfig にあり URL で変えられるので、コードを変えずに比較できる。
  GUARANTEED_TOP も比べるなら、VizConfig に追加する必要がある
- 01 の範囲では件数を変えない。current プリセットの回帰確認(neighborLimit=40)を崩さないため

## 6. 後から関わる人への引き継ぎ事項

- 相互リンクは作品内の記事で飽和する。順位への効き方は、ほぼ冒頭リンクの重みで決まる
- 重みを調整するときは `?debug=1` を付ける。Console の `console.table`(プール上位20件の m・mutual・lead・score)と、`[wikipedia]` の行(相互リンク件数・冒頭リンク件数・確定枠のうち morelike 圏外の件数)を見る
- 実 API を Node から連続で叩くと 429 になる。調査はブラウザ上で、間隔をあけて行う
- 所要時間の比較は1回の測定では当てにならない。複数回の中央値で判断する
- 表示件数・確定枠の比率の見直しは、02 の実装後に評価する(5.4)
