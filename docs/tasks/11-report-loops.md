**数字だけの報告。`EGG_CINEMATIC_MIN`(6)は変えていない。** 6件と7件のどちらを最上位の段階にするかは、この数字を見て試用の後に決める

## 測った条件

- 日付: 2026-09-29。展開結果は Node で Wikipedia から一度だけ取り、`tests/fixtures/long-walk-routes.json` に保存した
  (`scripts/fetch-long-walks.mjs`。表示と同じ `fetchLinkedArticles`、rev5 と同じ重み(rev2)・種 1・40件。1記事ごとに3秒あけた)
- 経路: 開始記事5件(初音ミク・流体力学・綾波レイ・コーヒー・富士山。09 の長い経路と同じ)× 歩き方2種類 = 10本。中心8件まで歩く
  - top: 毎回、まだ通っていない子のうち、関連スコアがいちばん高い記事へ進む
  - draw: 毎回、抽選の枠から出た子(11〜24位)のうち、まだ通っていない、いちばん順位が高い記事へ進む
  - 歩き方は `src/debug/walks.js` の `walkRoute`。保存したデータから毎回同じ経路になることと、09 の経路10本を作り直せることを
    `tests/walks.test.js` で確かめている
- 数え方: 経路の3件目以降の各時点で、今の中心の子のうち2つ以上前に通った記事(= クリックすれば輪が閉じる記事。表示の合図と同じ `loopCandidates`)を、
  輪の長さ別に数えた(`loopOpportunities`)。子は `neighborLimit` 件目までに切り詰める(同じ種なら、件数を減らした抽選は多い件数の抽選の先頭と同じ。09)
  - **時点**: その長さの輪を1つでも閉じられる時点の数 / **候補**: その長さになる候補の数(表の各マスは「時点 / 候補」)
- 表は `node scripts/count-long-walk-loops.mjs` で出した

- 取得のとき、4記事(初音ミク -Project DIVA-・富士登山・山小屋・全国地方公共団体コード)で冒頭リンクの取得が接続の失敗で抜けた(加点なしで順位が付く)ので、
  その4記事だけ取り直した。取り直しても経路は変わらなかった。Node の既定の User-Agent では HTTP 429 で断られたので、このスクリプトの中だけ
  問い合わせ元を名乗る User-Agent を付けた(アプリの fetch には付けない。CLAUDE.md の「Wikipedia への fetch に独自ヘッダを付けない」はブラウザの事前確認の話)

## まとめ(neighborLimit 24 = rev5)

- 3件目以降の 60時点のうち、輪を閉じられる時点は 40(67%)
- **6件以上の輪を閉じられる時点は 60時点中 11**(候補 14)。**7件以上は 7**(候補 8)
- 6件以上の輪は、中心が6件以上になってから(6件目以降)しか起きない。6〜8件目の 30時点に限ると、6件以上は 11時点(37%)、7件以上は 7時点(23%)
- 6件以上を閉じられる時点がある経路は 10本中6本、7件以上は 10本中5本。どちらも同じ話題の中を歩き続ける経路に集まる
  (コーヒーの2本で 6時点。話題が離れていく経路 — 富士山の2本・綾波レイの draw・初音ミクの top(標茶町 → 北海道 → 札幌市 と地名へ移る)— では 0)
- 09(中心5件の経路)で「5件の輪の候補は30時点中2件」だったのは、中心が5件までしか無かったため(5件の輪は5件目の1時点でしか起きない)。
  中心8件まで歩くと、長い輪を閉じられる機会ははっきり増える
- これは「閉じられる機会」の数で、実際に閉じるかは、利用者がその記事(訪問済みの中空の球。明るさの脈動の合図付き)を選ぶかによる

## 読み方の注意

- 開始記事5件・歩き方2種類だけの数字。実際の散歩は毎回いちばん関連の強い子や抽選の枠の先頭を選ぶわけではない
- top の歩き方は同じ話題の中にとどまりやすく、輪を閉じる機会が多めに出る。draw は話題が離れやすい
- 同じ時点で長さの違う輪を複数閉じられることがあるので、各長さの時点の数を足すと「輪を閉じられる時点」より多くなる
