# タスク07: 見せ方の簡素化と、到着時の共通ワード強調(rev4)

CLAUDE.md と SPEC.md(1章・6.1・6.3・6.5・6.7・6.9・12章)と、06 の基準値レポート(`docs/tasks/06-report-baseline.md`)を読んでから着手すること。
前提: 06(画面上の見え方を測る道具)が完了していること

## 背景と目的

05 では、関連の強さを距離・脈動・共通ワードのパケットで見せた。しかし、どれも「次にどれをクリックするか」の判断材料になっていなかった。

- 相互リンクは子の 97〜100% に付いていて差を生まない(01 と 05 で二度確認)。中心同士の線も、子をクリックして進めば、ほぼ必ず相互リンクになる
- 脈動やパケットは、1px の線や小さな点への「弱い足し算」で、飾りに見える
- 一方で、薄くする仕組み(二次ノードの不透明度・ホバーの減光・移動中の減光・ラベルの深さフェード・重なりの間引き)は機能ごとに足されてきた。そのため、重要なもの(前後の中心をつなぐ共通ワード)でも、カメラの角度しだいでラベルが読めなくなる

このツールでの面白さの定義(2026-09-26 利用者と合意。CLAUDE.md の目的):
面白さの本質は wiki 自体にあり、このツールはそれを 3D の形で届ける。**判断しやすい・操作しやすい・視認性が高い・ちゃんと動く、はすべて面白さを詰めることと同じ。**

そこで 07 では、**強調を「足す」のをやめ、「読めることを保証する」方針に切り替える。**

1. 相互リンクの脈動を、コードごと外す
2. 共通ワードのパケットを、新プリセット `rev4` では off にする
3. 前の中心から今の中心へ進んだ直後の数秒だけ、2つの中心と共通ワード(前後の中心の両方につながっている記事)以外を減光し、共通ワードの名前を確実に読めるようにする(**到着時の共通ワード強調**)
4. 薄くする仕組みとその例外を、SPEC の一か所の表にまとめる

利用者との合意事項(2026-09-26):

- 要点は「前後の中心の両方が、同じ記事(例: 鏡音リン・レン → ついなちゃん の間のエグジットチューンズ)と関係している」と認識できること
- 到着時の強調は**強調している間だけ**。強調が終わった後は、共通ワードも通常のルール(深さフェード・間引き)に戻す。ずっと目立たせると、意図が伝わらないまま画面を占めるため
- 見逃したときに再表示する手段は作らない(ステータス行の件数表示・再生ボタンも作らない)。簡素さを優先する。実装後に試してから、必要なら見直す
- 共通ワードが 0 件のときは何もしない
- 色は使わない。モードでの色分けは将来の候補として残す(下の「やらない・将来の候補」)
- 脈動は外した後、どの意味にも使わない。09 で「輪を閉じられる記事の合図」に使う予定(07 では実装しない)
- `rev3` は 06 の基準値として残す。今回の変更は新プリセット `rev4` で on にし、rev3 と並べて比べる
- 子の距離(関連スコアで子の線の長さを変える)は rev4 では使わない。3D では差がほとんど読み取れず、極端に差をつけると中心付近が混むため
- 中心同士の距離は rev4 でも使う。ただし相互リンクは使わず、共通ワードの件数を4段階に分けて決める(5章)。
  狙いは2つ。利用者に説明しなくても「共通ワードで距離が変わっている」と気づいてもらうこと、そして前後の中心を離して、09 で輪を閉じる線を目立たせること
- スマホの横画面では、前の中心が画面の外に出てもよい(画面の小ささによる限界として受け入れる)

## 用語

- **前の中心 / 今の中心**: 軌跡 `shown` の末尾から2番目 / 末尾
- **共通ワード**: 前の中心と今の中心の両方の `expansions` にある記事(05 の `sharedTitles`。中心自身は除く。並びは今の中心の `expansions` の順 = 関連スコアの順)
- **到着時の強調**: 仕様2の、到着直後に数秒だけ行う減光とラベルの保証

### 2. 到着時の共通ワード強調(`arrivalShared`)

**いつ始めるか**

- 軌跡の末尾に新しい記事を足して進んだとき(ノードのクリック・サイドバーの隣接記事のクリック)に限る。
  戻る(パンくず・Backspace・訪問済みノードのクリック)・検索・リセット・URL からの復元・追加表示(+ MORE)では始めない
- カメラが到着したとき(`TRAVEL_MS` 後。パンくずを更新するのと同じ時点)に始める。移動中の減光とは重ねない
- `trailEnabled=false`、軌跡が2件未満、共通ワードが 0 件のときは何もしない

**何を見せるか**

- 強調の対象: 前の中心・今の中心・共通ワードのうち、今の中心の並び順で上位 `arrivalSharedMax` 件
- 通常の明るさで残す線: 前の中心 ↔ 共通ワード(対象の分)、共通ワード ↔ 今の中心(対象の分)、前の中心 ↔ 今の中心
- それ以外のノードと線は、ホバー(6.1)と同じ比率(`HOVER_DIM_RATIO`)まで減光する。ラベルも、ホバーと同じく対象以外は隠す
- 対象のラベルは、強調している間だけ次の例外にする
  - 深さフェードを受けない(どの角度でも読める)
  - 重なりの間引きで、ほかのラベルより先に場所を取る(対象どうしの重なりは、今の中心の並び順が上のものを優先する)
- データパケットは今までどおり流す。通っている線が減光していれば、今までどおり一緒に薄くなる(6.7)
- 色・形・脈動は使わない(明るさの差だけで見せる)

**どう終わるか**

- `arrivalSharedMs` の間続け、`arrivalSharedFadeMs` かけて通常の表示に戻す。ラベルは既存の出入りのフェード(`LABEL_SWAP_S`)で戻す
- 次のいずれかが起きたら、その時点で打ち切って通常の表示に戻す(操作を奪わないため。カメラの追従が手動操作でやめるのと同じ考え方)
  - ドラッグ(回転)・ホイール・ズームボタン
  - ほかのノードへのホバー(ホバー表示に切り替える)
  - クリック・キー操作(次の移動・戻る・追加表示)
- `prefers-reduced-motion: reduce` のときは、減光と戻りを補間せずに即時に切り替える(強調そのものは行う)

**作り方**

- 対象の集合(ノードと線)は純粋関数 `arrivalHighlightSet(trail, expansions, max)`(`src/utils/relation.js`)で求める
- 表示は、ホバーの減光の仕組み(`applyHighlight` が目標を決め、`updateVisuals` が補間する)に、「隣接の代わりにこの集合を使う」状態として乗せる。
  仕組みを別に作らない。0 の報告で乗せられないと分かったら相談する

**設定**(VizConfig。見た目だけの項目 = `VISUAL_KEYS`。leva は relation フォルダ)

| 項目 | 既定値の目安 | 意味 |
|---|---|---|
| `arrivalShared` | current・rev2・mesh・rev3 は off、rev4 は on | 到着時の共通ワード強調 |
| `arrivalSharedMs` | 2500 | 強調を続ける時間 |
| `arrivalSharedFadeMs` | 500 | 通常の表示に戻す時間 |
| `arrivalSharedMax` | 8 | ラベルを保証する共通ワードの上限 |

値は実際に見て調整し、決めた値と理由を constants.js のコメントに残す。範囲は `RANGES` に置き、`current` と揃える。

### 4. プリセット `rev4`

- `rev4` = `rev3` から次を変えたもの
  - 脈動の項目は仕様1で消えるので、持たない
  - `sharedPackets`: off(パケットは rev2 と同じ「今の中心 → 上位の子」の流れ)

### 5. 距離の扱い(2026-09-26 利用者と決定)

**子の距離は使わない**

- rev4 では `childSpringMin` と `childSpringMax` を両方 `springLength`(55)にし、子の線の長さを関連スコアで変えない

**中心同士の距離は、共通ワードの件数の段階で決める**

細かく比例させず、大きな段階で分ける。利用者に説明しなくても「共通ワードで距離が変わっている」と気づいてもらうのが目的なので、段階の違いがはっきり見えることを優先する。

| 共通ワードの件数 | 段階 | 距離 | 設定 | 初期値の目安 |
|---|---|---|---|---|
| 0 | none | かなり遠い | `trailLenNone` | 180 |
| 1〜3 | few | 遠め | `trailLenFew` | 130 |
| 4〜7 | mid | 普通 | `trailLenMid` | 95 |
| 8 以上 | many | 近め | `trailLenMany` | 60 |

- 段階の境目(3 と 7)は constants.js の定数(`TRAIL_TIER_FEW_MAX`・`TRAIL_TIER_MID_MAX`)にする。利用者が決めた割り振りなので、調整するのは距離の値の方で、境目は動かさない
- 相互リンクは使わない
- 新しい設定 `trailTiered`(rev4 だけ on)で切り替える。off のときは 05 の計算(基準から相互リンクと共通ワードの数で縮める)のままにし、rev3 の配置は変えない。
  段階の設定は配置に効く項目なので、`VISUAL_KEYS` には入れない。範囲は `RANGES` に置く
- 段階の長さには子の最小値(`childSpringMin`)の下限を掛けず、そのまま使う
- 段階を決める純粋関数 `trailTier(sharedCount)` と、段階から長さを返す関数を `src/utils/relation.js` に置く
- 距離の値は、実際の距離(反発で狙いより長くなる)で段階がはっきり分かれるように調整する。
  目安は、隣り合う段階の実際の距離に 1.3 倍以上の差があること。決めた値と理由を constants.js のコメントに残す
- 共通ワードの件数は画面に出ている分で数える。そのため、今の中心で + MORE を押すと件数が増えて段階が変わり、前後の中心が近づくことがある。仕組みに気づくきっかけにもなるので、そのままでよい
- スマホの横画面では、前の中心が画面の外に出てもよい

### 6. 06 の道具への追加

- `measure()` の既定の `presets` を `['rev2', 'rev3', 'rev4']` にする(3つとも順位付けの重みが同じなので、06 の決まりのまま比べられる)
- 項目を1つ足す
  - M9 共通ワードの読める件数: 前の中心がある経路(`work`・`science`・`voice` のすべて)で、共通ワードのうち上位 `arrivalSharedMax` 件について、ラベルが読める状態の件数を、周回視点の**最悪値**と平均で出す。
    `arrivalShared` が on のプリセットは「強調が最も効いている時点」の状態で、off のプリセットは通常の状態で測る(同じ件数の枠で比べる)
- 中心同士の距離を結果に載せる: 経路の隣り合う中心の組ごとに、共通ワードの件数・段階・線の狙いの長さ・実際の 3D 距離・最初の視点での画面距離(仮想画面ごと)
- 経路の一覧(`benchRoutes`)に、段階 few と mid の組を含む経路を足す(候補は 0 の報告で挙げる)。
  既存の3本には、none(流体力学→マグネシウム)と many(初音ミク→鏡音リン・レン、マグネシウム→ウラン)の組しかないため

## やらない・将来の候補(00-workflow.md と SPEC 11章に反映する)

**やらない(2026-09-26 利用者と合意。再提案しない)**
