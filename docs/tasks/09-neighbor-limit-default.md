# タスク 09: 表示件数の見直しと、既定プリセットの切り替え

CLAUDE.md と SPEC.md(3.3・6.10・12章)と、01 の評価レポート(5.4)・07 と 08 の完了報告・測定レポートを読んでから着手すること。
前提: 08(最初のカメラ距離の見直し)が完了していること

## 背景と目的

このツールでは、面白さを詰めること = 判断しやすい・操作しやすい・視認性が高い・ちゃんと動くこと、と定義している。
07 の議論で、「強調を足しても伝わらない」ことが分かった。判断しやすさに最も素直に効くのは、**選択肢そのものを減らすこと**である。

- 01 の評価レポート(5.4)では、表示件数を減らすことに賛成し、11位以降の記事(声優など)は 02 の追加表示でまとめて出せる、と整理済み
- 07・08 の測定で、スマホの横画面は中心付近が非常に混んでいることが分かっている

このタスクでは、表示件数(`neighborLimit` と関係する値)を測定して決め直す。
そのうえで、詰めの段階の区切りとして、**既定のプリセットを rev2 から新しいプリセットに切り替える**(2026-09-26 利用者と合意)。

## 表示件数を変えると影響するもの(このタスクの注意点)

07〜10 の仕組みは、どれも「画面に出ている子」を元に数えている。そのため、件数を減らすのは設定を1つ変えるだけでは済まない。

1. **中心同士の距離の段階**: 共通ワードは前後の中心の両方の子に出ている記事なので、子を減らすと共通ワードの件数も大きく減る。
   段階の境目(3件と7件)は、利用者が 40件を前提に決めた割り振りである。減らした後は、ほとんどの組が「遠め」や「かなり遠い」に寄るおそれがある
2. **到着時の共通ワード強調**: 見せる共通ワードの数が減る
3. **輪を閉じたときの演出(10)**: 輪を閉じるには、前に通った記事が今の中心の子として画面に出ている必要がある。子が減ると輪ができにくくなり、「3件の輪で規則に気づいてもらう」という狙いに響く

そのため、件数の判断と段階の境目の扱いを、同じ測定の結果を見ながら一緒に決める。
**段階の境目は利用者が決めた割り振りなので、Claude Code は案を出すだけにし、自分では変えない。**

## やること

### 0. 着手前の報告(ここで一度止まる)

1. `neighborLimit`・確定枠(`GUARANTEED_TOP`)・抽選の枠・追加表示で一度に足す件数の、今の関係
2. 件数を変えたときに影響する箇所の一覧(上の3つのほかにあれば)
3. 下の1章の `measure()` の拡張のやり方
4. 指示書と現在のコードとのずれ

### 1. `measure()` の拡張: 順位付けに効く値が違う変種も比べられるようにする

- 06 では、顔ぶれの違う結果を黙って比べないよう、順位付けに効く値(`neighborLimit` など)が違うプリセットどうしを比べるとエラーにしていた。
  このタスクでは、`allowDifferentRanking: true` を指定したときだけ、変種ごとに展開し直して比べられるようにする
- 展開し直しは、同じ `seed`・同じ実行の中で行う。結果には、顔ぶれが違う比較であることを明記する
- 変種は 08 で足した `variants` の形で指定する(例: `{ name: 'n30', base: 'rev4', overrides: { neighborLimit: 30 } }`)
- 足す測定の項目
  - 共通ワードの件数と段階の分布: 経路の隣り合う中心の組ごとの、共通ワードの件数・段階・実際の中心同士の距離
  - M10 輪を閉じられる候補の数: 経路の各時点で、今の中心の子のうち、2つ以上前に通った記事の数(10 の演出の起きやすさの目安)

### 2. 候補を測って比べる

08 を終えた rev4 を土台に、少なくとも次を同じ `measure()` の実行で比べる。

| 変種 | `neighborLimit` | `GUARANTEED_TOP` | 抽選の枠 |
|---|---|---|---|
| n40(今) | 40 | 10 | 30 |
| n30 | 30 | 10 | 20 |
| n24 | 24 | 10 | 14 |

ほかによい組み合わせ(確定枠を減らす、追加表示で一度に足す件数を変えるなど)があれば足してよい。

見る項目と優先順:

1. M5・M6(混み具合・押し間違い。特に phone)がよくなること
2. M3・M9(上位と共通ワードの読める件数)が悪くならないこと
3. 共通ワードの段階の分布が、偏りすぎないこと(4つの段階がそれぞれ現れること)
4. M10(輪の候補)がなくならないこと

### 3. 結果を報告して、利用者の判断を待つ(ここで一度止まる)

- 変種ごとの比較表(全経路 × pc/phone)と、段階の分布の表を出す
- おすすめの件数と、その理由を書く
- 段階の境目について、「今のまま(3件・7件)」と「件数に合わせた境目の案」の両方で段階の分布を示す。どちらにするかは利用者が決める

### 4. 利用者の判断を反映して、既定プリセットを切り替える

- 新しいプリセット `rev5` = 08 を終えた rev4 に、利用者が決めた件数(と、変える場合は段階の境目)を足したもの
- `DEFAULT_PRESET` を `rev5` にする。current・rev2・rev3・rev4 は比較のために残す
- `?preset=` の付いていない URL を開いたときの見た目が変わる。以前に共有された URL の中に `preset` の付いていないものがありうるかを確かめ、報告する(12.3)
- 段階の境目を変える場合も、定数の値と理由を constants.js のコメントに残す

## テスト(tests/)

- `allowDifferentRanking` を指定しないときは、今までどおりエラーになる
- 変種ごとに展開し直した結果が、同じ `seed` なら毎回同じになる
- `rev5` の各値が、利用者が決めた値になっている。`DEFAULT_PRESET` が `rev5` になっている
- current・rev2・rev3・rev4 の配置とカメラ距離が、08 完了時と一致する(展開結果を保存したファイルで確かめる)
- 既存のテストがすべて通る

## 実機確認(09 の後に利用者が行う。10 の前提)

09 が終わったら、詰めの段階の締めくくりとして、利用者がスマホの実機で次を確かめる。
Claude Code は、確かめる手順(公開 URL またはローカルの URL の開き方を含む)を完了報告に書くこと。

- スマホの横画面で開き、トップバー・ドロワーが操作できる
- ノードのタップで、狙った記事に進める(押し間違いが気にならない)
- 到着時の共通ワード強調が見える
- 回転・ズームの操作が引っかからない。フレームレートの体感に問題がない
- 縦画面での案内表示が出る

見つかった問題は、10 に入る前に別のタスクとして扱う。
