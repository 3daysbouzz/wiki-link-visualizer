## 進め方のルール

### 最初に1回だけ

1. 01〜03 をすべて読み、全体像を把握する
2. 実装に入る前に、次の点を報告して止まる
   - 指示書同士の矛盾・依存関係の問題
   - 指示書と現在のコードとのずれ(指示書が前提にしている構造が実際と違う、など。
     特に、実装済みの VizConfig 化・横画面対応の結果と食い違う箇所)
   - 実装順を変えた方がよい理由があればその提案
3. 利用者の返答を待ってから 01 に着手する

(01〜04 はすでに完了済み。05 から再開する場合は、この「最初に1回だけ」は
 タスク05単体を対象に行う。すなわち、05 を読んで CLAUDE.md・SPEC.md・現在のコード
 (特に buildGraph・Graph3D.jsx の力学計算・expansions のデータ形)とのずれがないかを
 確認し、報告してから着手する)

### 各タスクで

1. 着手前に、そのタスクの指示書と CLAUDE.md・SPEC.md の関係箇所を読み直す
2. 実装する。指示書どおりにできない・指示書より良い方法がある場合は、
   **勝手に変えずに**、その時点で止まって理由を添えて相談する
3. 完了条件を自分で確認できる範囲で確認する(`npm test`・`npm run build`・Console のエラーなど)
4. タスク単位でコミットする(1タスク = 1コミット以上。複数タスクを1コミットに混ぜない)
5. SPEC.md・README.md・CLAUDE.md の更新も、そのタスクのコミットに含める
6. 下の「報告の形式」で報告し、**そこで必ず止まる**

### 止まる・待つ

- 利用者が「OK、次へ」と言うまで、次のタスクに進まない
- 利用者が修正を頼んだら、同じタスクの中で直して、もう一度報告して止まる
- **main への push は、利用者が「push して」と言うまで行わない。**
  push すると GitHub Actions で公開サイトに自動反映されるため、
  利用者がローカルで見た目と操作を確認してから公開する
- 「OK、次へ」と言われたら、上の表の状態を更新してコミットしてから次のタスクに進む

## 報告の形式

```
## タスク NN 完了報告

### 変更点
- (何をどう変えたか。ファイル名と要点)

### 指示書から変えた点・判断した点
- (なければ「なし」)

### 自分で確認したこと
- npm test: 結果
- npm run build: 結果
- その他

### 利用者が確認すべき手順
1. (npm run dev で開く URL、試す操作、期待する見え方を具体的に)

### 気になっている点・次のタスクへの影響
- (なければ「なし」)

### コミット
- (コミットの一覧。push はまだしていないこと)
```

確認手順はターミナル操作に不慣れでも実行できるよう、コマンドは丸ごとコピーできる形で書くこと。

### 公開を広げる前に必須

- **スマホの実機確認**(利用者が行う): 09 の確認項目(トップバー・ドロワー・タップの狙いやすさ・到着時の強調・回転とズームの軽さ・縦画面の案内)に加えて、輪の演出。
  特に、6件以上の並べ替えがスマホの横画面に収まるか(`window.__viz.egg(6)` で確かめられる)
- **デバッグモードを公開用のビルドから外す**: 実機確認と身内の試用が終わってから行う。デバッグパネル(leva)・`measure()`・`egg(n)` などは
  開発時(`npm run dev`)だけ使えるようにする。`?preset=` で見た目を切り替える仕組みは、共有された URL の再現に使うので残す
- **Wikipedia への問い合わせの作法の確認**: 利用者が増えると、問い合わせが人数に比例して増える。Wikimedia がブラウザからの API 利用に求めている、
  問い合わせ元の名乗り(`Api-User-Agent` ヘッダ)などに対応しているかを確かめる

### 身内の試用の後に決める

- 輪の候補の合図を出す件数(今は候補すべて)
- 破線の部分の輪の見え方
- 中心同士の距離の段階で、few(1〜3件)と none(0件)の実際の距離の差が足りていない件(07 から持ち越し。
  「共通ワードで距離が変わることに、説明なしで気づいてもらう」という狙いに直結する)
- 到着時の強調で名前を保証する件数(今は1件。08 の報告にある、2件以上にできるかの数字を参考にする)
- 輪の最上位の段階を6件のままにするか、7件にするか(11 の報告 `11-report-loops.md` の数字を参考にする)
- 輪の演出の時間割と見た目の細かい調整(11 で作り込んだものを、試用の感触で直す)

### 身内の試用で聞くこと

- 輪の演出に気づいたか
- 共通ワードの数で、中心同士の距離が変わることに気づいたか
- どこで迷ったか、押しにくかったか

`?debug=1` の `[egg]` ログは、普通に使う人からは集まらないので、試用の記録には使わない(開発者が自分で試すときの確認用)。
