# タスク 08: 最初のカメラ距離の決め方を見直す(rev4)

CLAUDE.md と SPEC.md(4章・6.10・12章)と、07 の完了報告・測定レポート(`docs/tasks/07-report-measure.md`)を読んでから着手すること。

## 背景

07 で rev4 に「中心同士の距離の段階」を入れた結果、共通ワードが 0 件の組(none)は、中心同士が 540〜580 前後まで離れるようになった。今のカメラは「全体が画面に入る」距離で決めているため、全体が広がると最初のカメラが大きく引いてしまう。

- science 経路で、最初のカメラ距離が 1.3 倍前後に伸びた(07 の測定では 966 → 1231)
- その結果、中心付近の混み具合(M5)と近すぎる組の数(M6)が悪化した(07 の報告・測定レポートに「既知の制限」として記録済み)

同じ原因で、ほかにも2つの問題が起きている。

- 共通ワードの名前を保証できるのが1件にとどまった。共通ワードが多い組では、前後の中心が画面上で pc 約19px・phone 約9px しか離れていないため
- スマホの横画面は、段階の設定と関係なく、元から混んでいる。M5 が 38〜41 で、一次ノードのほぼすべてが中心から 60px 以内に集まっている

このタスクでは、rev4 の最初のカメラ距離を、「全体が入る」ではなく「今の中心の周りが見やすい」基準で決めるように変える。

このツールの目的(CLAUDE.md)では、ノードを大量に見せることは目的ではなく、「次にどれをクリックするか」を判断しやすくすることを優先する。そのため新しい決め方では、表示中の子を**すべて**画面に入れることにはこだわらない。**関連スコアの上位の子が確実に見えて、読めること**を優先する。

## 前提

- 07 は案 A(ラベルを別の位置に置くルール + 共通ワードを前の中心より先に置く、保証件数 N = 1)で完了していること
- 07 のコミットがすべて push されていること(Web 版で作業する場合は必須)
- 既定のプリセットは rev2 のまま変えない。rev4 を既定にするかは、09 で決める

## 数字の比べ方(このタスク全体の決まり)

07 で分かったとおり、Wikipedia 側の変化で、展開結果と測定の数字は1時間のうちにも変わる。そのため、次の決まりで比べる。

- プリセットや候補どうしは、**同じ `measure()` の1回の実行の中で**並べて比べる。以前の報告に書かれた数字(絶対値)とは比べない
- 配置とカメラ距離の回帰は、07 と同じく**展開結果を保存したファイル**で確かめる(Wikipedia の変化の影響を受けないようにするため)

## やること

### 0. 現状の調査(実装前に報告し、ここで一度止まる)

コードを変える前に、今のカメラ距離がどう決まっているかを整理し、最初の報告に含めること。

- 初回表示・子をクリックして進んだとき・戻る(パンくず・Backspace・訪問済みノード)・追加表示・URL からの復元のそれぞれで、カメラ距離がどこで、何を基準に決まるか
- 利用者が手でズームした後に進んだ場合、その距離が保たれるのか、決め直されるのか
- 画面の大きさが変わったとき(ウィンドウの大きさの変更、スマホの縦横の切り替え)の扱い(SPEC 4章「高さが変わったら縮尺を保つ」との関係)
- 06 の `measure()` が、最初のカメラ距離をどの関数で求めているか(表示と同じ関数を呼んでいるか)

調査の結果、下の方針で想定していない動き方をしていた場合は、実装に入る前に止めて相談すること。

### 1. カメラ距離の決め方を設定として足す

- カメラ距離の基準を選ぶ設定を新しく足す(名前は既存の設定の付け方に合わせてよい。例: `cameraFit`)
  - 今の決め方(全体が入る)を既定値とし、rev4 だけ新しい決め方にする
  - current・rev2・rev3 のカメラの動きは一切変えない
- 力学(配置)には手を入れない。カメラは配置の結果を見るだけにする
- 表示と `measure()` は、同じカメラ距離の関数を呼ぶ(06 の「表示と同じ計算を使う」の決まりのとおり)
- 候補の比較のために、`measure()` で設定を上書きした変種を並べて測れるようにする(例: `variants: [{ name, base: 'rev4', overrides: { cameraFit: 'a' } }]`)。候補ごとにプリセットを増やさない

### 2. 新しい決め方の候補を比べて選ぶ

少なくとも次の候補を試し、測定して一番よいものを選ぶこと。ほかによい案があれば足してよい。

- 候補 a: 今の中心とその子(表示中のもの)がすべて入る距離
- 候補 b: 候補 a に加えて、前の中心も入る距離(ただし上限を設ける)
- 候補 c: 候補 a を基本に、前の中心が画面の端に収まる場合だけ含める
- 候補 d: 今の中心と、関連スコアの上位の子(確定枠 `GUARANTEED_TOP` 件)がすべて入る距離。残りの子は画面の外に出てもよい

候補 d を加える理由: 子が1件でも遠くに飛んでいると、候補 a ではカメラがそれに引っ張られて引いてしまう。上位の子を基準にすれば、外れた位置の子に左右されにくい。

選ぶときの優先順:

1. 下の完了条件をすべて満たすこと
2. 07 で決めた共通ワードの読みやすさ(N = 1 が周回の最悪でも読める)を崩さないこと
3. スマホの混み具合(phone の M5・M6)がよくなること
4. 前の中心がなるべく画面に入ること(つながりの流れが分かるため。ただし、画面の外に出ることは許容すると合意済み)
5. 移動のたびにカメラ距離が大きく変わりすぎないこと(毎回ズームが揺れる感じにならないこと)

### 3. 移動時の動き

- 子をクリックして進んだときも、同じ基準でカメラ距離を決める
- 利用者が手でズームしていた場合の扱いは、0 の調査で分かった今の動き方を保つ(変える必要があると判断したら相談すること)
- 「動きを減らす」設定のときの扱いは、今のカメラ移動と同じ規則に従う

## 測る項目(06・07 の道具に足す)

- 最初のカメラ距離
- 表示中の子のうち、初期視点で画面内に入っている割合
- 確定枠の子(上位 `GUARANTEED_TOP` 件)が、初期視点ですべて画面内に入っているか
- 前後の中心の、初期視点での画面上の距離(px)。共通ワードの名前を何件保証できるかに直結するため
- 前の中心が、初期視点で画面内に入っているか
- 移動ごとのカメラ距離の変化: 経路の隣り合う移動の前後で、カメラ距離の比(大きい方 ÷ 小さい方)の最大値

## 完了条件

- 同じ `measure()` の実行の中で、rev4(新しい決め方)の science 経路の M5 と M6 が、rev3 の値と同じかそれ以下になる(pc と phone それぞれ、初期視点と周回の平均の両方)
- ほかの経路(work・voice・coffee・段階を確かめる経路)で、rev4 の M5・M6 が、同じ実行の中での 07 の決め方(`cameraFit` を今の決め方にした rev4)より悪くならない
- phone の M5・M6 が、同じ実行の中での rev3 より悪くならない
- 初期視点で、今の中心と確定枠の子がすべて画面内に入る(pc と phone の両方)
- 共通ワードの読みやすさ: 保証した上位1件が、共通ワードのある全経路・pc と phone・周回の最悪でも読める(07 の条件を維持)
- current・rev2・rev3 のカメラ距離と配置が、07 完了時と末尾の桁まで一致する(展開結果を保存したファイルによる回帰テストで確認)
- rev4 の配置(中心同士の距離の段階)が 07 完了時と一致する(同上)
- `npm test` がすべて成功し、`npm run build` が成功し、Console にエラーが出ない

## 測定と報告に含めるもの

06・07 の測定の道具を使い、次の表を報告に入れること。どの表も、同じ `measure()` の1回の実行で測ったものにする。

- 候補ごとの比較表: 全経路 × pc/phone ごとの、最初のカメラ距離・M5・M6・M9・子が画面に入っている割合・前後の中心の画面距離・前の中心が画面に入っているか・移動ごとのカメラ距離の比の最大値
- 決めた方式での、rev2・rev3・rev4 の比較表(09 で rev4 を既定にするかを判断する材料にするため)
- 参考情報: 新しいカメラ距離で、共通ワードの保証件数 N を 2 以上にできそうか(初期視点・周回の最悪の両方)。**このタスクでは N は変えない**。数字の報告だけでよい

## 範囲外(このタスクではやらないこと)

- 力学の値(硬さ・段階の長さ・反発など)の変更
- ラベルの置き方・並び順・保証件数 N の変更
- 表示件数(`neighborLimit` など)の変更(09 で扱う)
- 既定のプリセットの変更(09 で扱う)
- カメラの自動回転など、新しいカメラの動きを足すこと(輪を閉じたときのカメラワークは 10 で扱う)

## 相談して止まる条件

- どの候補でも完了条件を満たせないとき(満たせない条件と、いちばん近い候補の数字を添えて)
- 前の中心を画面に入れることと、M5・M6 の改善がぶつかって、どちらかを諦める必要があるとき
- 0 の調査で、手動ズームの扱いを変えないと方針どおりにできないと分かったとき
